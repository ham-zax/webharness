# X Content Workflows

Use only the branch that matches the task. Keep outputs compact; do not expose internal scoring unless it helps the decision.

## Create

1. Identify the content object: idea, source post, release, result, observation, benchmark, conversation, project evidence, or argument.
2. Establish verified facts and the account's additive thesis before choosing presentation.
3. Choose the smallest format that naturally carries the contribution: Original, Quote, Reply, Thread, or Article.
4. Load relevant private memory when enabled: `voice.md`, `patterns.md`, `results.md`, `topics.md`, and active `voice-experiments.md` only as needed.
5. If the format is Article, read `articles.md` and follow the Article branch below.
6. Draft a small number of materially different options only when useful. Vary thesis, evidence emphasis, framing, or structure rather than synonyms.
7. Check the final candidate for factual support, voice fit, comprehension, additive value, and whether it stops after the payoff.
8. Return the strongest draft first.

Do not let a writing strategy or source morphology outrank the account voice.

## Discover / select a fresh opportunity

Read `discovery.md`.

1. Start from current Growth OS candidates and their canonical `sourceKinds` when available.
2. Treat source presence as provenance, not a quality vote. `x_for_you` is not proof of virality; `x_creator_latest` is not proof of relationship strength.
3. Rank content opportunities by the actual contribution available: relevance, freshness, source/context value, relationship continuity when real, evidence confidence, and whether Hamza has something distinct to add.
4. Prefer reciprocal or high-value creator conversations when the contribution belongs there, but do not force a Reply when a Quote, Original, Article, Watch, Research, or Ignore decision is stronger.
5. After selecting an X candidate, inspect enough exact live source/thread context through `agent-browser` before writing when current context can change the decision.
6. Do not bulk-open every candidate. Discovery is triage first; deep inspection follows selection.

## Improve / critique

Diagnose before rewriting. Fix the highest-value defect rather than touching every sentence.

Check:

- **Object:** Is the real model/tool/API/result/failure/question visible early enough to understand the post?
- **Contribution:** Is this Hamza's addition or mostly source paraphrase?
- **Evidence:** Are factual/first-person claims actually supported?
- **Voice:** Does it sound like a builder speaking naturally, or like institutional analyst copy?
- **Morphology:** Is clever symmetry, a hidden-boundary frame, or a generalized lesson being forced where simpler phrasing would land better?
- **Payoff:** Does the useful judgment arrive early?
- **Depth:** Is it as short as the act permits but as long as the consequence requires?
- **Stopping point:** Does the post keep explaining after it has already landed?

Then return the strongest rewrite and, only when useful, one materially different alternative.

## Reply

1. Read the source and enough thread context to know what has already been said.
2. Choose the actual social act before choosing a technical archetype.
3. Find one missing contribution or social payoff.
4. Use only the depth that act needs.
5. Stop after the payoff.

Valid Replies include:

- terse agreement or support;
- celebration or enthusiasm;
- humor or social observation;
- direct answer;
- implementation detail;
- caveat or boundary condition;
- comparison or correction;
- evaluation design or decision metric;
- informed question;
- relationship callback;
- de-escalation.

Do not add a technical wrinkle merely to prove intelligence. Do not explain the source back to the author. If no useful seam remains, recommend no Reply.

## Article

Read `articles.md`.

### Full Article request

Use this sequence:

`opportunity -> contribution/evidence type -> thesis -> reader promise -> title/opening/outline/visual concept -> draft -> evidence/usefulness review -> reusable package if needed -> launch copy if requested`

Do not force every optional stage into the final output. The internal sequence is for reasoning; the visible deliverable should match the user's requested scope.

### Scoped Article request

- **Title request:** return title options only, grounded in the actual article promise.
- **Outline request:** return the smallest outline that fulfills the promise.
- **Review request:** diagnose promise, evidence, usefulness, provenance, and voice defects; do not rewrite everything unless asked.
- **Visual/thumbnail request:** return a content brief; image generation belongs to the image tool.
- **Launch-hook request:** return launch copy only; do not rebuild the Article.
- **Package request:** specify the smallest useful artifact set; Git/GitHub mutation belongs to its governing tools.

## Learn from outcomes

1. Gather the exact post/output, source/context, format, timing/age, and measured results. Use `account-analytics.md` when authenticated own-account analytics materially improve the evidence.
2. Preserve discovery provenance when available (`x_for_you`, `x_creator_latest`, `x_momentum`, `x_latest`) as context, not as an X ranking factor.
3. Separate writing features from distribution/context variables: source reach, relationship, topic momentum, media, account stage, timing, crowding, measurement window, and experiment assignment.
4. Keep reach, engagement, profile discovery, follow conversion, and relationship quality distinct.
5. State the observed result before proposing a lesson.
6. Propose the narrowest supported candidate lesson and record competing explanations/counterexamples.
7. Use low/medium confidence by default; reserve high for repeated evidence with few credible alternatives.
8. If persistence is authorized and the private workspace is enabled, update `results.md` and append candidate lessons to `candidates.md` using `evidence-and-memory.md`.
9. Do not promote a candidate unless the governing workflow authorizes promotion and the evidence threshold is met.

## Format selection notes

- **Original:** durable owned insight/proof that stands without borrowed context.
- **Quote:** source context is useful and Hamza has a distinct additive thesis.
- **Reply:** the contribution belongs inside the live conversation.
- **Thread:** the reasoning genuinely needs sequence but remains short-form X content.
- **Article:** the reader benefit needs materially more depth, evidence, examples, or artifacts than a Thread can comfortably carry.

If one idea fits in a strong Original or a short Thread, use the smaller format.

## Variant quality

Bad variants preserve the same thesis and merely change adjectives, punctuation, or sentence order.

Good variants differ in a real decision dimension, for example:

- builder reaction vs evidence-first explanation;
- practical consequence vs supported judgment;
- direct answer vs informed question;
- concise observation vs deeper technical breakdown.

Do not generate many variants merely to create choice.
